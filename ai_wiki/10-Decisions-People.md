# 人物同定に関する決定記録

## 2026-07-18: Vaultは同定ヒント、DBは確定結果を保持する

### 決定

- Obsidian Vaultの人物ノートは、人物名・aliasを人が記述する入力元として扱う。
- DBは、サマリ上の表記をどの人物へ結び付けるかを確定・保持する場所とする。
- UIで人が確定した別名は、`person_aliases`に永続化し、以後のサマリ取り込みではVault入力より優先する。

### 理由

Vaultのaliasは編集しやすい一方、表記衝突や一時的な記述ミスを含み得る。Vaultを即時の唯一の正本にすると、1ファイルの不備で同期全体を止めたり、誤った自動吸収を起こしたりする。人が確認して確定した同定結果をDBに保持することで、同じ表記を安定して再利用できる。

## 2026-07-18: Vaultノートの問題は全停止ではなく、個別スキップとレポートにする

### 決定

- loaderはノート単位の不備や衝突で全体を例外停止しない。
- フロントマター不備、重複ID、正規名衝突は、該当ノートを同期対象から除外してレポートする。
- alias衝突は、共有aliasだけを照合対象から除外する。各ノートのID・正規名・他の一意なaliasは利用する。
- Vault由来の問題はDBに履歴保存せず、同期時・API要求時に現在のVaultを再検査してレポートする。

### 理由

人物ノートは独立して編集されるため、1枚の誤記で日次・週次サマリなどの処理全体が失敗するのは運用負荷が高い。問題を可視化しつつ安全な入力を継続利用すれば、誤同定を避けながら通常処理を止めずに済む。

## 2026-07-18: Vault alias衝突は候補・吸収処理に流さない

### 決定

- 複数のVaultノートが同じaliasを主張する場合、そのaliasは`person_candidates`に変換しない。
- 衝突aliasは候補吸収、旧人物の統合、自動マージの照合条件に使わない。
- 解決はUIでは行わず、Obsidian側の人物ノートを修正して行う。

### 理由

同じaliasを複数人物が主張している状態では、どの人物へ紐付けるべきかを自動判定できない。既存の候補吸収ロジックへ渡すと、複数人物への誤吸収が起こり得るため、衝突は同定処理から完全に隔離する。

## 2026-07-18: DB確定別名とVault入力が矛盾した場合はDBを維持する

### 決定

- サマリ人物解決の優先順位は、`person_aliases`のDB確定別名、衝突していないVault入力、未解決候補とする。
- DB確定別名と異なる人物をVaultが主張しても、DBの紐付けを上書きしない。
- Vault内でもaliasが衝突している場合は、DBの確定先とVault側の全主張者を含む複合衝突としてレポートする。

### 理由

UIでの確定は人による判断済みの結果であり、後から入力されたVault記述だけで黙って変更すると履歴の同定が不安定になる。不一致は明示し、Vaultを修正するまで自動吸収を止めることで、安全性と追跡可能性を両立する。

## 2026-07-18: UIで解決した未解決候補は競合検査して永続化する

### 決定

- `person_aliases`は`normalized_name`を一意にし、1つの表記を1人だけへ確定する。
- 候補解決では、同じ別名が別人物へ確定済み、または別人物の正規名と衝突する場合、HTTP 409で拒否してDBを変更しない。
- 解決先はVault連携済み人物に限定する。解決成功時は別名を保存し、既存サマリの候補紐付けを移管して候補を削除する。

### 理由

表記を複数人物へ確定すると、次回以降の取り込みで再び曖昧になる。競合を明示的に拒否し、既存の確定先や重複統合フローを案内することで、DB上の同定を一貫させる。

## 2026-07-18: 重複の自動検出は確定一致に限定する

### 決定

- 自動表示する重複候補は、未連携人物の名前が安全なVault名・aliasに一致する場合、または同一の非NULL `vault_id`を持つ複数行に限定する。
- 未連携人物どうしの類似・同名推定は自動候補にしない。
- 人物統合ではVault連携人物を残し、未連携人物または同一Vault IDの重複行だけを統合元として許可する。異なるVault IDを持つ人物同士は統合しない。

### 理由

人物の表記揺れや同姓同名はあり得るため、類似判定だけで統合候補を出すと誤統合の危険が高い。確定的な一致だけを自動化し、それ以外は利用者の明示操作に委ねる。

## 2026-07-18: 任意人物統合における許可範囲と衝突時の拒否方針

### 決定

- **統合の許可範囲**:
  - 未連携からVault連携への統合 (未連携 → Vault連携)
  - 同一の `vault_id` を持つ人物同士の統合
  - 未連携人物同士の統合 (未連携 → 未連携)
- **統合の拒否範囲**:
  - 異なる `vault_id` を持つ人物同士の統合
  - Vault連携済み人物を未連携人物へ寄せる統合 (Vault連携 → 未連携)
- **衝突時の拒否方針**:
  - 統合元の正規名または別名（`person_aliases`）が、統合元・統合先以外の第三者の正規名または登録別名と衝突する場合は、情報を捨てずに統合全体を拒否する。
  - 統合元の表記が統合先の正規名または登録別名と一致する場合は、同一人物として統合する明示操作なので許可する。その際、重複する別名は1件に一本化し、同じ表記を重複保存しない。
- **サマリ参照の連結**:
  - 統合元のサマリ参照は統合先へ移管する。
  - 同一サマリを両者が参照している場合は、既存のメモ内容を改行連結し、表示順は先頭側を維持（`min(display_order)`）して1件に統合する。

### 理由

任意統合において、異なるVault IDを持つ人物同士や連携済みから未連携への統合は、意図しないデータ不整合を招くリスクがあるため制限する。また、第三者との衝突を伴う統合を強制すると、人物同定の一貫性が崩れる恐れがあるため全体を拒否することで安全性を保証する。

## 2026-07-18: 文脈別の人物割当と一括 alias 解決の制限

### 決定

- **文脈別個別割当の実装**:
  - 同じ曖昧表記（例: 山田さん）をサマリ（文脈）ごとに Vault 連携済み人物へ個別に割り当て可能とする。
  - 手動個別割当用のテーブル `summary_person_assignments` を追加し、`summary_id + normalized_name -> person_id` のマッピングを保存・永続化する。
  - サマリ再生成時（`upsert_summary`）は、この手動個別割当を最優先（Priority 0）で適用し、リンクを復元する。
  - 個別割当時にはグローバルな `person_aliases`（別名）は作成せず、同じ表記が新しくサマリに現れた場合は常に未解決候補として扱う。

- **グローバル alias 解決（一括解決）の禁止**:
  - 手動での個別割当が1件でもある表記（`normalized_name`）については、UI・API・同期処理のすべてにおいてグローバル alias 解決（一括解決・自動吸収）を禁止する。
  - 既存の候補一括解決 API（`resolve_person_candidate`）は、同表記に手動個別割当が存在する場合は HTTP 409 Conflict で拒否し、DB を変更しない。
  - 同期処理（`sync_people`）の Step B において、手動個別割当がある表記の未解決候補は Vault alias から自動吸収せず、スキップする。

- **人物統合時の追従**:
  - `merge_people` 実行時、統合元の手動個別割当（`summary_person_assignments` の `person_id`）も統合先へ追従・移行する。

### 理由

「山田さん」のように頻出かつ複数の同姓同名が存在する曖昧表記について、グローバルに別名（alias）を登録すると、すべてのサマリで誤同定が起きてしまう。サマリ（日付や週）という文脈ごとに個別解決できるようにし、さらに個別割当済みの表記はグローバル解決や同期の自動吸収から隔離（禁止）することで、過去の正しい同定状態を破壊することなく、安全かつ柔軟な人物同定と整合性を維持できる。

## 2026-07-22: 未解決候補を未連携人物として昇格できる操作の追加

### 決定

- **昇格操作の追加**:
  - `POST /api/v1/people/candidates/{candidate_id}/promote` を追加する。
  - リクエスト: `display_name`（必須）。
  - レスポンス: 作成した `PersonDetail`。
  - 空名は 400、候補不存在は 404、手動個別割当・正規名・alias 競合は既存形式の 409 で拒否する。

- **トランザクション処理**:
  - 1 トランザクションで、`people` に UUID の `person_id`・`vault_id=NULL` を作成し、候補の全 `summary_person_candidates` を `summary_people` へ移管して候補を削除する。
  - 同一サマリに既存リンクがあれば、既存どおりノートを連結し最小の表示順を採用する。
  - 入力した人物名と候補表記が異なる場合だけ、候補表記を新人物の `person_aliases` に保存する。同じ場合は正規名のみを保存する。

- **サマリ再取り込みの解決順変更**:
  - 手動個別割当 → DB確定 alias → 安全な Vault 入力 → **未連携人物の正規名との完全一致** → 未解決候補の順とする。
  - これにより、候補名のまま昇格した人物も次回取り込みで再候補化されない。

- **既存同期の扱いは変更しない**:
  - 後日、Vault ノートの主名が昇格人物の主名と完全一致すれば、既存の未連携人物と同様に同期で Vault 連携へ更新される。
  - Vault alias だけの一致は、DB 確定 alias 優先の現行仕様を維持する。

- **一括解決との差分**:
  - 既存の「Vault 連携人物への一括解決」と「文脈別個別割当」は Vault 連携人物限定のまま維持する。
  - 手動個別割当済みの表記は、昇格も一括解決も不可とする。

### 理由

未解決候補の中に、Vault にノートを持たない人物が含まれることがある。従来は手動個別割当しか手段がなかったが、昇格操作を追加することで、候補を新規人物として確定し、以後の取り込みで自動解決できるようになる。Vault 連携なしで独立した人物として扱えることで、柔軟な人物管理が可能になる。

## 2026-08-09: 人物未解決候補の却下・アーカイブと再開管理

### 決定

- **却下（アーカイブ化）の仕様**:
  - 候補表記単位で「却下」を記録し、状態を `rejected` として管理する。
  - 却下された候補は未解決候補一覧（`status = 'unresolved'`）から除外し、新設される「却下済み候補」アーカイブへ移管する。
  - 既存・将来のサマリに同一の表記が現れても、新しく未解決候補に戻したり再作成したりせず、既存の却下候補レコードを再利用し状態を維持する。

- **操作の制限**:
  - 却下状態（`status = 'rejected'`）の候補に対する解決、昇格、個別サマリ割当は、直接実行できないように制限する。操作を試みた場合は、HTTP 409 Conflict（`candidate_rejected`）を返して再開を促す。
  - 却下候補を解決・昇格・割り当てしたい場合は、アーカイブから明示的に「再開」を行って `unresolved` に戻す必要がある。

- **自動同期からの除外**:
  - Vault 同期（`sync_people`）の自動解決・吸収対象は `status = 'unresolved'` の候補のみに限定する。
  - 却下済み候補は、Vault の alias や主名と完全一致しても自動解決・削除しない。

### 理由

ノイズとなる表記揺れや無関係な固有名詞がサマリから抽出された際、それを一時的ではなく永続的に除外する手段が必要である。表記単位でグローバルに「却下」状態を保持することで、サマリ再生成や将来の取り込み時にノイズが再浮上するのを防ぎつつ、可逆な操作として「再開」を担保することで、柔軟かつ安全な人物同定と整合性を両立する。

## 未連携人物の編集・人物削除とサマリ数順表示

| 項目 | 内容 |
|------|------|
| 決定日 | 2026-07-18 |
| カテゴリ | 人物管理 |
| 決定内容 | 未連携人物のみを編集可能とし、削除はDBのみの完全削除（Vaultノートは削除しない）とする。また、旧主名変更時は別名として残さない。 |

### 結論に至った経緯

1. **Vault連携人物は編集不可とする方針:**
   - Vault連携人物の表示名や確定別名をUIで直接編集できるようにすると、Vault側のMarkdownフロントマターとの間で不一致（ドリフト）が発生し、次回同期時に情報が上書きされて戻るなどの混乱を招く。そのため、編集操作は未連携人物（`vault_id` なし）にのみ制限する。
2. **削除はDBのみでVaultノートを残す方針:**
   - すべての人物（未連携・連携済み）に対して「DBからの完全削除」を提供する。
   - Vault連携人物の場合、Vaultノート（Markdownファイル）自体は人が管理するソースオブトゥルースであるため、システムが勝手にファイルを削除することは避ける。
   - 削除確認時に、Vaultノートが残るため、次回同期で再作成され得ることをUIで明確に明示することで、誤操作や期待値のズレを防ぐ。
3. **未連携人物の主名変更時に旧主名を自動別名化しない方針:**
   - 表示名の変更（タイポの修正など）を行った際、古い名前を自動で確定別名として残してしまうと、意図しない同定衝突（409）を誘発する。古い主名は自動別名化せず、完全に置換するシンプルな挙動を採用する。

## 人物編集競合時の統合自動提案

| 項目 | 内容 |
|------|------|
| 決定日 | 2026-07-19 |
| カテゴリ | 人物管理・UI |
| 決定内容 | 未連携人物の編集で主名または別名の競合 (409) が発生した場合、エラー表示に統合案内を追加し、統合先セレクトに競合人物を自動選択する。統合は自動実行せず、利用者の明示操作（プレビュー→実行）に委ねる。 |

### 結論に至った経緯

編集中に主名重複 (main_name_conflict) または別名重複 (alias_conflict) で保存が409拒否された場合、競合相手は同一人物である可能性が高い。従来はエラーメッセージを表示するのみだったが、統合への導線がないため利用者が気付かず放置されるリスクがあった。競合人物を統合先セレクトに自動設定し、エラー内に案内を表示することで、統合プレビュー確認という安全なフローに誘導する。

### トレードオフ

自動設定はあくまで提案であり、利用者が別の統合先を選択したり、統合を全く行わないことも可能。保存に失敗した編集内容はフォームに残るため、主名を調整して再送信する選択肢も維持される。競合人物が人物一覧に存在しない場合は自動設定をスキップする。

## PeoplePage 分割リファクタリング

| 項目 | 内容 |
|------|------|
| 決定日 | 2026-07-31 |
| カテゴリ | フロントエンド・人物管理 |
| 決定内容 | 1,652行に肥大化した PeoplePage.tsx を、機能単位の内部コンポーネント（CandidateTab, PeopleListTab, DuplicatesTab, VaultReportTab, MergePreviewDialog 等）へ分割する。表示コンポーネントは状態を所有せず、親である PeoplePage がすべてのタブ、ダイアログ、選択状態、フォーム、通知および操作ハンドラを統括する。 |

### 結論に至った経緯

肥大化したコンポーネントの可読性、保守性を向上させるため、単一ファイル内の表示責務を機能（タブ・ダイアログ）単位で物理分割した。この際、各タブの表示や詳細切り替えなどの状態をサブコンポーネント内に閉じ込めてしまうと、タブ切り替え時や画面再読み込み時に選択された詳細状態、編集用フォームの入力値、統合提案などの状態が失われてしまい、ユーザー体験が著しく低下する。

そのため、以下の基本構造を採用する：
- **表示コンポーネントの制御化（無状態化）**: すべてのサブコンポーネントは、必要な値、表示状態（モバイル詳細表示の開閉、競合情報、エラー、ローディング）、および操作イベントのみをPropsとして親から受け取る「完全制御コンポーネント」とする。
- **親ページによる操作と状態の統括**: 親である `PeoplePage.tsx` がすべての状態（選択された候補/人物、各フォームの入力値、統合プレビューリクエストの競合回避カウンタ等）を所有し、操作ハンドラを一元管理する。
- **API通信の切り出し**: `features/people/peopleApi.ts` に各HTTPリクエストを名前付き関数として集約し、コンポーネントと通信・型の依存を整理する。

これにより、既存の操作フローやタブ切り替え時の状態保持、モーダルのフォーカス制御、二重送信防止などの挙動を完全に維持したまま、保守性の高い分割構造を実現する。

### 仕様および決定事項

1. **診断とグルーピングの基準:**
   - 承認済みメモリから、同一の `memory_key`、正規化本文の一致、および既存の埋め込み類似度閾値（`0.85`）以上の関連グループを形成する。
   - `valid_until` や `review_due_at` の期限超過、または最新エビデンスの `observed_at`（ISO 8601 または YYYY-MM-DD をJSTに正規化）が基準日から180日以上前のものを、古さによる再評価（失効）候補に含める。エビデンス日付がない場合は古さによる失効候補にしない。

2. **LLM診断プロンプトと構造化JSON (`config/prompts/memory_maintenance.md`):**
   - 共通のプロンプトにて、初回診断・フィードバック・スナップショット不一致時の再診断を共通処理する（`input_mode` で動作を切り替え）。
   - LLMには `merge`, `correct`, `expire`, `no_action` の構造化JSON配列のみを返却させる。根拠が不十分な場合は `correct` を提案せず `no_action` とする。
   - `merge` / `correct` は正本ID（`main_id`）、吸収ID群（`absorbed_ids`）、統合後本文（`integrated_content`）、根拠（`reason`）を必須とし、対象メモリが提案内・複数提案内で重複しないことを検証する。

3. **HITL Run 登録とチェックポイント (`memory.apply_maintenance_proposals`):**
   - 1診断全体を1つの `HitlRun` に、各提案を1件の `HitlQuestion`（選択肢: 「適用」「見送り」「フィードバックして再提案」）として登録。
   - 提案が0件の場合はRunを作らず終了する。
   - チェックポイントには基準日、提案ラウンド、提案内容、対象ごとの `updated_at` スナップショット、適用済み提案IDリストを保持する。

4. **安全かつ冪等なハンドラ適用ロジック:**
   - 物理削除は行わず、歴史保持のために不要なメモリは `expired`、統合・訂正で吸収されたメモリは `superseded` に状態遷移させる。
   - 適用前に対象メモリの最新の `updated_at` と登録時のスナップショットを検証し、不一致（競合）がある提案のみを最新状態で個別再診断する。
   - 「フィードバックして再提案」が選択された場合はコメント入力を必須（UI・APIの両方でバリデーション）とし、元提案・コメント・最新状態をLLMに渡して該当提案だけを次のラウンド（`round_2` 等の新質問セット）として再提示する。
   - 各提案はそれぞれ独立したトランザクションで確定され、正本には `maintenance_merged`/`maintenance_corrected`、吸収側には `maintenance_superseded` の専用の `memory_events` を記録。変更適用後はMarkdown投影（`approved.md`）を自動更新する。

## 未連携人物への候補一括解決

| 項目 | 内容 |
|------|------|
| 決定日 | 2026-08-14 |
| カテゴリ | 人物管理・人物同定 |
| 決定内容 | 未解決候補の一括解決先は、Vault連携済み人物だけでなく既存の未連携人物も許可する。 |

候補の解決は候補表記をグローバルな確定別名として保存し、全サマリ参照を移管する操作である。未連携人物でも `person_aliases` とサマリ再取り込みの解決順は同じように機能するため、Vault ID の有無はシステム上の制約ではない。昇格と人物統合を別々に実行すると、後段の統合失敗時に昇格済み人物だけが残るため、既存の一括解決トランザクションを直接利用する。

- 却下済み候補、文脈別手動割当済み候補、第三者の正規名・別名との衝突は、従来どおり拒否する。
- 未連携人物への解決後にVaultが同じ表記を別人として主張した場合は、DB確定別名を優先して不一致をレポートする。未連携人物の主名とVaultノートの主名が一致すれば、既存同期により同じ人物レコードへVault IDを付与する。
- UIは確認ダイアログを増やさず、未連携人物を選んだ場合の同期上の注意と、一括解決が将来の同表記にも適用されることを明示する。
