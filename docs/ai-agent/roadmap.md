# Web AI エージェント ロードマップ (v1 後)

AgentsPage (v1 完成済み) を起点とする UX 改善とコンテキスト拡張のロードマップ。
各項目は独立したフェーズとして実装可能だが、依存関係（モバイル対応 → ピン留めの表示 → 検索など UI を前提とするもの）に注意。

ユーザコンテキスト (2026-08-25 確認):

- モバイル (実機) で AgentsPage を使う。→ モバイル1ペイン化が最優先の基盤となる。
- セッション蓄積は現時点で数個程度。→ 検索 (#5) は当面緊急度が低め、ただし将来を見据えて早期着手でもよい。

## 優先順位 (固定)

### Tier S — まず最初 (基盤 UX・低コスト高効果・リスク小)

#### #1 モバイル1ペイン化 + 3 ペイン畳み
- **背景**: Memory/VaultSearch/Research/Hitl ページは `lg:hidden` トグル + オーバーレイ引き出しパターンを採用済み (`App.tsx:135-153,161-168`, `VaultSearchPage.tsx:154`, `MemoryPage.tsx:166` 等)。AgentsPage だけ未対応 (`AgentsPage.tsx:971` で `lg:flex-row` のみ)で、モバイルでは2 ペイン積みが常に表示される。
- **スコープ**:
  - エージェント一覧 (上段) と会話履歴 (下段) を 1 つの左ペインにまとめ、モバイルでは `lg:hidden` ハンバーガー + 固定オーバーレイ引き出しで開閉する。
  - チャット領域にはヘッダー左に「エージェント/会話」選択ボタンを置き、押すと左ペインを全画面モーダル表示する。
  - デスクトップでは現行の 2 ペイン表示を維持し、追加トグルで左ペインを畳めるようにする。
- **影響**: 以降のすべての機能の UI 基盤。#2/#3/#4 の表示もこの基盤に載せる。
- **見込**: 1-2 日。確立パターン踏襲なのでリスク低。

#### #2 入力途中の自動下書き保存
- **背景**: セッション切替 / ブラウザリロード / 偶発的な他ページ遷移で `inputText` と `pendingAttachments` (Phase 1 添付) が失われる。
- **スコープ**: `localStorage` に `agent-draft:{session_id}` のキーで `{ text, attachments, savedAt }` を debounce 200ms で保存。セッション切替時・送信成功時にクリア。`pendingAttachments` は base64 を含むためセッションあたり上限 5 枚 × 8MB を超えると容量が気になりはじめる → 容量逼迫時の古いセッション削除や別ユーザー指定タブでの漏洩防止は Phase 3 候補。
- **影響**: UX 安定度向上。
- **見込**: ~1 日。バックエンド不要、フロントのみ。

#### #3 入力欄2段化 + UI アイコン化
- **背景**: 現状の入力フッターは `テンプレート` / `画像` / `textarea` / `送信` が1段横並びで幅が狭く、モバイルで入力域が圧迫される。エージェントヘッダーの `設定編集` / `削除` もテキストボタンで視認性が低く、記号ベースのアイコンも混在している。
- **スコープ**:
  - アイコンライブラリ `lucide-react` を導入。既存のインライン SVG / 記号（✕ ▶ ◀ ▼）も順次アイコン化。
  - 入力欄を2段化: 1段目=textarea（全幅）、2段目=`[+]` ポップオーバーメニュー（テンプレート選択 / 画像アップロード）＋モデル名ミュート表示＋送信アイコンボタン。
  - エージェントヘッダー: `設定編集` → 歯車アイコン(`Settings`)、`削除` → ヘッダーから除去し編集フォームヘッダー左にゴミ箱アイコン(`Trash2`)を配置（編集時のみ）。
- **影響**: 以降の機能の入力 UI 基盤。#6 `/` コマンドはこの2段レイアウト上に載せる。
- **見込**: ~1.5 日。

#### #4 エージェント・会話のピン留め
- **背景**: お気に入りのエージェント/進行中の会話を素早く切り替えたい。
- **スコープ**:
  - DB: `agents.pinned_at` / `agent_sessions.pinned_at` 列追加 (migration v25)。nullable、ピン留め解除は null に戻す。
  - 左ペイン一覧で pinned 先頭、その後は `updated_at DESC` で並べる。
  - ピン留めボタン (📌) を各行に配置。
- **影響**: アクセス速度と視認性向上。
- **見込**: ~1 日。

### Tier A — 次に着手 (価値高・中コスト)

#### #5 チャット履歴検索
- **背景**: セッションが蓄積するほど「以前のあの会話を参照」が難しくなる。現状は個人用途で数個なので緊急性低めだが、価値は時間とともに伸びる。
- **スコープ**:
  - `GET /api/v1/agent-sessions/search?q=...` で全エージェントの `agent_messages.content` を LIKE 検索する。エージェント名・会話タイトル・snippet・ヒットした `message_id` を、メッセージ単位で返す。検索インデックスは初期は DB の LIKE で十分、件数が 100+ になってから FTS5 移行を検討。
  - 会話一覧ペインの上部に横断検索ボックス。ヒットごとにエージェント名、会話タイトル、メッセージ抜粋 (1-2 行) を表示する。
  - フロント: debounce 200ms。結果選択で対象エージェントと会話を開き、該当 `message_id` の要素へスクロールする。
- **影響**: ナレッジ蓄積系の基本機能。
- **見込**: ~2 日。

#### #6 `/` でコマンド (プロンプト呼び出し) [完了]
- **背景**: 既存の「テンプレート」ボタン (`AgentsPage.tsx` の template selector dropdown) は機能するが、UI 的には `/` トリガーの方が標準的かつインクリメンタル絞り込みが便利。
- **スコープ (実装済み)**:
  - チャット入力の先頭が `/` の時に textarea 直上にコマンドパレットを表示。
  - `/` 単体で全テンプレート (最大 8 件) を表示。短縮形 (`/テンプレート名`) と明示形 (`/template テンプレート名`) の両対応。末尾スペース無しの `/template` は名前に 'template' を含む/で始まるフィルターとして処理。
  - 大小文字無視で `startsWith` 該当が上位、次いで `includes` 該当。同ランク内は `display_order` の順序を維持。
  - キーボード操作: `ArrowUp`/`ArrowDown` でラップアラウンド選択移動、`Enter` で選択（送信は行わず入力置換＋フォーカス保持）、`Escape` でパレット閉じる、`Ctrl+Enter` で即時送信。
  - 既存の `+ → テンプレート` ボタンと `/` コマンドパレットが共存。
- **影響**: テンプレート入力の高速化。
- **見込**: 完了。

#### #7 会話タイトル自動生成
- **背景**: 現状は `agent_sessions.title = clean_content[:30]` (`store.start_user_run` のフォールバック) で、最初のユーザー入力の先頭 30 文字がそのままタイトル。日本語では文脈の切れ目が悪いことが多い。
- **スコープ**:
  - 1 往復目 (user + assistant 1 つ) が完了した `complete_run` 後に、LLM で短いタイトル (例: 「ユーザー入力とアシスタント応答を踏まえた 15-25 字タイトル」を返す純粋関数) を生成。
  - `runtime.complete_run` 後に `generate_session_title()` を `await asyncio.to_thread` で呼び、`store.update_session_title` で更新 (既存の完全 LLM ログ基盤に乗せる)。
  - 2 回目以降のメッセージでは生成しない (タイトル上書きで履歴が消えないよう、ユーザが PATCH で編集可能にしておくのが理想)。
- **影響**: セッション一覧の可読性向上。
- **見込**: ~1 日。

### Tier B — 高価値・高コスト

#### #8 `@` でコンテキスト参照 (Vault ファイル・人物・プロジェクト)
- **背景**: 現在は LLM に「Vault の〇〇ノートを見て」と自然文で頼むしかない。明示的に `@` で挿入すれば (1) LLM が見落とさない、(2) UI で入力内容を可視化できる。
- **スコープ**:
  - `@` キーで autocomplete ポップアップを開閉 (`Mention` パターン)。
  - 検索ソース: (a) Vault ファイル → 既存の `/api/v1/vault-search`, (b) 人物 → `/api/v1/people`, (c) プロジェクト → `PlannerProject` を返す API (要確認・なければ新規)。
  - 挿入形式: `@vault:相対パス`, `@person:人物名`, `@project:プロジェクト名` のようなコロン区切りプレースホルダ。LLM には通常テキストとして渡す (モデルに解釈させる)。LLM 側がツールで実体にアクセスする形。
  - ポップアップ UI: fuzzy match、最大 8 件程度、上下キーで選択 Enter で確定。
- **影響**: 会話の明示性と LLM のヒット率向上。
- **見込**: 2-3 日。

#### #9 LLM が参照した外部情報へのリンク表示
- **背景**: `memory_search` / `vault_search` / `web_search` のツール結果を「LLM はこの情報を見て答えた」と UI で示したい。
- **スコープ**:
  - runtime 側: `tool_call_end.result` パースに加え、`metadata` (source_paths / memory_ids / urls) を SSE `tool_call_end` に追加。
  - フロント側: 該当ツール (`memory_search`, `vault_search`, `vault_read_file`, `web_search`, `web_extract`) については `Source: <list>` のセクションをツール結果 `pre` の中にレンダリング。各ソースに `Link` もしくは hover でコピーボタン。
  - 既に web_search/vault_search の結果には `metadata` (`source_path` etc.) が含まれる。runtime 経由で抽出するだけでフロントレンダリングの追加実装が主。
- **影響**: 透明性と信頼性向上。
- **見込**: ~2 日。

### Tier C — 後回し可 (既存機能と重複)

#### #10 会話履歴の要約と Vault 保存
- **背景**: 既存のデイリーサマリー生成 (`summary/`) と構造が被る。エージェントセッションを「長くなったから要約して Vault に保存したい」用途とデイリーサマリーは粒度が違う (前者: 1 セッション、後者: 1 日) ので共存価値はあるが、必要性が明確になるまでは後段でよい。
- **スコープ**:
  - `POST /api/v1/agent-sessions/{id}/summarize-to-vault` で全メッセージ → LLM 要約 → `vault-note/{date}-agent-{session_id}.md` のテンプレートで書き出し。
  - 既存の HITL と統合して「書き出し確認」を促すか、自動書き出しにするか設計判断必要。
- **見込**: 2-3 日 (要確認事項あり)。

## フェーズ提案 (実装順まとめ)

| Phase | 含まれる Tier | 内容 | 累計見積 |
|---|---|---|---|
| Phase 3 | Tier S (#1〜#4) | モバイル対応 + 下書き保存 + 入力欄2段化 + ピン留め | ~5-6 日 |
| Phase 4 | Tier A 1 (#5〜#7) | 検索 + /コマンド + タイトル生成 | ~4 日 |
| Phase 5 | Tier B (#8〜#9) | @ 参照 + 参照リンク表示 | 4-5 日 |
| Phase 6 | Tier C (#10) | Vault 書き出し (必要性確認後) | 2-3 日 |
