# 週次チェックインをHITLの問いとして配信し、先週の一歩を参照する

## Status

Accepted（自由記述2問版に更新: 2026-10-30）

## Context

Weekly Reflection は1か月間で0件だった。一方、同じ LINE 通知経路を使う週次メモリ
インタビューは12週連続で3/3問が回答されており、回答時刻は作成から12〜104時間後に
散っている。両者の差は通知の有無ではなく、次の3点である。

- 問いが用意されていること（下書きは「読むもの」で、読むと完了する）
- 未回答の状態がシステムに残ること（HITL Run は `pending_user` として一覧に残る）
- 答えた後に何かが起きること（インタビューは記憶候補になる）

既存の日曜17:30の週次下書き通知は本文を LINE に流すだけで、読めば満たされる。
本人は本文を LINE で読むことに価値を置いておらず、リンクで開ければ十分としている。

Phase 1 は「初期の根拠はユーザー入力した Goal / Focus / Reflection だけに限定する」と
していたが、この制約の根拠は、初期の縦切りで根拠を狭く保つことと、全ユーザー情報を
返す汎用 Capability を作らないことにある。質問生成が対象週のノートを読むことを禁じる
ものではない。実際、メモリインタビューの質問は日次ノートから生成されている。

また、質問の質は先週の答えを読むことで上がり、「自分の答えが次の問いに現れる」ことが
継続の報酬になる。通知を増やさずに閉ループを1本作れる点で、他の反映先より効率がよい。

## Decision

- 配信は既存の日曜17:30 のスロットを使い、週次下書きの通知を週次チェックインの通知に
  置き換える。LINE は HITL Run へのリンクのみを送り、下書き本文を直接送る形は採らない。
- 週次下書きの生成と週次ノートへの保存は継続する。1週間のうちに忘れている出来事を
  思い出す材料として残すためで、通知としては送らない。下書きは「通知」ではなく
  「保存物」として併存し、置き換えるのは通知だけとする。
- 自由記述の質問は2つにする。1問目「今週は Focus に向けてどんな1週間でしたか」は、
  直近に回答された週の `next_week_scope`（本人が決めた一歩）を必ず参照する。
  未回答の週を挟んでも、直近の回答があれば触れる。回答が一度もなければ参照しない。
  2問目「来週試したいこと」（任意）がそのまま次の `next_week_scope` になる。
  `continue` の週にも次週の一歩が残るため、毎週ループが閉じる。
- 同じ回答画面に「来週はどうするか」の4択（continue / narrow / change / pause）を置く。
  `change` のときだけ切替先 Focus を選ぶ。`narrow` を選んだ場合は「来週試したいこと」が
  必須になる（既存モデルの `next_week_scope` 必須制約を維持するため）。
  決定は保存後変更不可という既存の規則を維持する。
- 質問生成は、対象週の日次ノート・週次ノートを読んでよい。読む範囲はその週の質問生成に
  限定し、全ユーザー情報を返す `user_context_snapshot` のような汎用 Capability は作らない。
- 回答期限は Run 作成から7日間（`expires_at`）とする。期限切れの必須質問がある Run は
  既存の失効処理で自動キャンセルされ、その週は Reflection なし（欠測）として扱う。
  未回答の催促や再通知は行わない。
- 複数の Goal が有効な場合、直近の Reflection が最も古い（または未記録の）Goal を選ぶ。
  優先順位ではなくローテーションとし、毎週の選択は直近の回答状況だけで決める。
- 参照はするが、未達を失敗状態にしない。「やらなかった」「忘れた」を同等の回答として
  扱い、streak・達成率・未達通知を導入しない（`proactive-plan.md` の非目標を維持する）。
  質問は、先週の一歩に触れなくても回答が成立する形にする。
- 回答は既存の Reflection 登録経路に写像する。1問目の回答は `learnings` に、
  2問目の回答は `next_week_scope` に入れる。`worked_well` と `difficult_reason` は
  空を許す。決定（continue / narrow / change / pause）は
  自由記述から推定せず、既存の Focus 状態遷移と Coach Thread Event に反映する。

## Consequences

- Phase 1 の「手動の Web 内 Reflection に限定し、Scheduler と外部通知を使わない」は
  置き換わる。[coach-goal-and-history.md](coach-goal-and-history.md) の該当箇所は
  この ADR を正とする。
- `review_draft` の送信経路が変わる（LINE テキストから通知＋リンクへ）。下書きの生成
  と保存は残るが、読まれない週が増える可能性がある。
- 回答画面は「2問＋4択」になる。`change` を選んだ週だけ切替先の追加入力が要る。
  2問目は任意とし、空でも送信できる。決定は既定の選択肢を置かず、選ばずに送信
  できないようにする（決定を推定しないため）。
- 週次の HITL Run が増える。メモリインタビューと同じ週に走るため、曜日・時刻・通知の
  重なりを設計する必要がある。
- 質問生成の入力範囲が広がるため、どの記録を根拠にしたかを表示・追跡できる形にする。
- 直近に回答された週がない場合だけ文脈が切れる。その場合は Focus と下書きだけから
  問いを生成し、生成自体は止めない。
- 質問の質が「先週の一歩を参照する」ことに依存するため、参照が形式的になった場合は
  効果が薄い。

## Alternatives

- 週次下書きのまま「チェックインがまだです」とリマインドする: 未達の催促であり、
  開いた先が詳細フォームのままなので、0件だった経路に圧力を足すだけになる。不採用。
- Web の Coach 画面に未完了表示を足す: 実測で Web を開く動線がない（Reflection 0件に対し
  HITL は12週連続）。不採用。
- 先週の答え全体を材料として渡し、何を参照するかは生成側に任せる: 安全だが弱く、
  当たり障りのない問いに収束しやすい。まず `next_week_scope` の参照を検証する。
- 週次で Goal との結びつきまで言語化する: 1週間では Goal との距離は変わらず、同じ結論の
  反復になる。抽象度の高い言語化は別の周期に置く。

## Open

- 回答を長期 memory へ書き戻すか。メモリインタビューと重複するため、この ADR の範囲外とし、
  別の判断として扱う。
- Goal との結びつきの言語化をどの周期で行うか。本人が判断するため、この ADR では決めない。
- 週次下書きを通知しない運用で、下書きが読まれないことの扱い。

## 見直す条件

3週間運用して、次のいずれかが起きたらこの決定を見直す。

- 回答が続かない、または先週の一歩を参照した問いへの回避（未回答の増加）が起きる。
- 参照が形式的になり、問いの質が上がったと感じられない。
- 週次の問いが達成チェックとして機能し、未達の圧力を生んでいる。
