# 自動ロールバックを行わず、構造化トレースと HITL で復旧する

## Status

Accepted

## Context

タスクは Vault 編集・Git リポジトリ変更・コマンド実行など、性質の異なる副作用を混在させる。
これらを横断して原子的に取り消す仕組み (トランザクション・スナップショット・git revert 等) は
実装コストが高く、Vault と外部 CLI の作用を完全に巻き戻すことは原理的に困難。

一方で、ワーカー停止・ツール失敗・ユーザー取消は必ず発生する。復旧の方針を決める必要がある。

## Decision

- **自動ロールバックを行わない**。途中失敗時も取消時も、実施済み変更は残す。
- 実施済み変更・未実施手順・復旧案を記録して HITL (WebUI) へ返す。
- 実行中の取消は**協調的取消**: 新しいステップを開始せず、実行中ツールへ中止要求し、
  途中変更をトレースへ記録する。取消はロールバックを意味しない。
- 常駐ワーカー停止時に実行中だったタスクは `interrupted` とし、**再起動後に自動再実行しない**。
  二重実行防止のため、人間がトレースを確認して再計画・再承認する。
- ツールの自動リトライは Capability Manifest／Adapter が宣言した範囲でのみ行い、
  枯渇したら停止して原因と再開案を HITL へ返す。
- 監査の正本は SQLite 上の構造化 Trace Event (追記のみ、機密値 redact)。
  LLM の非公開思考過程は保存せず、全入出力を無条件に保存する仕様にもしない。

## Consequences

- 失敗・取消の後始末は人間の判断に委ねられる。トレースの品質 (変更一覧・復旧案の記録) が
  復旧の使いやすさを直接決める。
- 半端な状態の Workspace が残り得るため、利用者はトレースと変更一覧を見て手動で修復する場合がある。
- 自動再実行しないため、復旧は必ず人間の確認を挟む。二重実行・二重変更のリスクを構造的に下げる。

## Alternatives

- **自動ロールバック (スナップショット復元 / git revert)**: Vault と外部 CLI の混在した副作用を
  原子的に戻すのは困難で、誤復元のリスクが高い。不採用。
- **自動再実行 (再起動後に queued へ戻す)**: 失敗原因が残ったままの二重実行を誘発する。不採用。
- **全入出力の無条件保存**: 監査性は上がるが、秘密値漏洩面と保存量の問題が大きい。redact＋要約方針を採用。
