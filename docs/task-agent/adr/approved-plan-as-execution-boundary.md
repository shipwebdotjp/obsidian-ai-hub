# 承認済み計画を実行境界にする

## Status

Accepted

## Context

オーケストレーターに Vault・Git リポジトリへの読取・作成・編集・削除・コマンド実行を
許す方針を採る場合、人間は「何に何をするか」を事前に確認できる必要がある。
削除のような不可逆操作を、実行中の逐次承認で守るか、計画の一括承認で守るかが論点。

既存の coding orchestrator は計画と実行の分離を持つが、タスク全体の計画承認と
逸脱時の再承認はまだ持たない。

## Decision

- 計画 (目的・手順・ツール／委譲先・対象・想定変更と副作用・完了条件) を作り、
  **タスク全体を WebUI で一括承認**する。ステップ単位の承認はしない。
- **削除は、計画に対象と効果が明記されている場合、通常の一括承認で許可する**。専用の追加承認はしない。
- 承認済み計画からの**逸脱が必要になったら停止**し、改訂計画を作って再承認 (`waiting_reapproval`) を求める。
- 差戻しには理由が必須で、同じタスク ID のまま再計画・再承認へ回す。
- **承認後に対象の最新状態が変わっていても、MVP では最新状態に対してそのまま実行する。**
  承認時スナップショットとの一致保証はしない。

## Consequences

- 人間の関与は承認時点に集約され、実行中の承認待ちで止まりにくくなる。
- 一方で、承認時と実行時の対象状態の乖離 (他タスクや手作業による変更) を技術的に防げない。
  このリスクは明示的に受容し、トレース監査と差戻し・取消で対処する。
- 逸脱検知の厳密な機械判定は MVP では提供しない (オーケストレーターの自己申告＋トレース監査)。

## Alternatives

- **ステップ単位の逐次承認**: 安全だが、長いタスクで人間の負担が大きく MVP の趣旨 (完遂品質より
  状態遷移・HITL・監査の完全性) に合わない。不採用。
- **承認不要の自動実行**: 削除やコマンド実行を人間の事前確認なしに走らせるのは信頼境界に反する。不採用。
- **スナップショット一致保証 (承認後に対象変更があれば自動停止)**: 実装コストと誤停止が大きく、
  MVP の範囲を超える。将来課題として記録。
