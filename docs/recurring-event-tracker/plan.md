# 定期記録・リマインダー実装プラン

## 境界

新しい定期記録ドメインを追加する。人物属性、外部Apple Reminders、既存のScheduler Job設定とは状態を共有しない。時刻ベースの評価だけは既存の `job_runner` に追加し、独自のWebサーバーtickは作らない。

## 永続化とサービス

1. SQLite migrationで、イベントタイプ、タイプ別プロパティ定義と選択肢、シリーズ、シリーズのプロパティ値、実行記録、通知試行を追加する。
2. サービス層で、タイプ・シリーズ・記録の作成、更新、削除、一覧・詳細表示、次回予定日と集計値の算出を実装する。
3. シリーズの同一性はタイプIDと正規化済みプロパティ組合せで保証する。記録の回数寄与は開始記録だけ任意、後続記録は1として保存する。
4. 記録の写真は共通メディア取込を通して `media_id` として保存する。メディア削除側では、定期記録から参照中の画像を競合として拒否する。

## APIとWeb UI

1. タイプ、シリーズ、実行記録の一覧・詳細・作成・更新・削除APIを追加する。シリーズ作成APIはプロパティ、間隔、開始記録、初期回数を一括で受け付ける。
2. 記録作成・更新APIは画像を最大1枚受け付け、応答には既存メディア参照を含める。通常の記録作成・更新では回数を受け付けない。
3. Web UIに「定期記録」画面を追加する。最初の画面はシリーズの現在地一覧とし、タイプ管理、シリーズ作成、記録追加、記録編集・削除、詳細履歴を提供する。
4. 期限日・期限超過を視認できる並びと状態表示を用意する。写真のない記録はサムネイル領域を空表示にする。

## 通知処理

1. `job_runner` のロック内処理に、JST 9:00以降の期限判定を加える。
2. 各対象について、通知試行を一意にclaimしてcommitした後、既存通知Publisherを使ってブラウザ／LINEへ送る。
3. 配信設定無効、送信成功、送信失敗を通知試行へ記録し、同じシリーズ・期限日の再評価では外部送信しない。
4. 通知ペイロードは表示用名称とリンクだけで構成し、メモ、写真、内部IDは渡さない。

## 文書化と運用

1. ユーザーガイドに、タイプ・シリーズ・実行記録、間隔、通知条件、写真の扱いを追加する。READMEには詳細を追加しない。
2. データモデル、月間隔の月末丸め、送信前claimによる一回通知は変更コストが高いため、実装時にアーキテクチャ決定記録へ理由を残す。
3. 実装完了時は隔離sandboxで写真付き記録、期限判定、既存通知設定に従う送信、記録削除を確認し、実データを使う場合は作成した識別可能な確認データを削除する。
