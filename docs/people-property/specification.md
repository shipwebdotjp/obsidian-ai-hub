# 人物属性 v1 仕様書

関連文書: [実装計画](implementation-plan.md) / [作業チェックリスト](todo.md) / [v2 以降ロードマップ](v2_roadmap.md)

本書は人物属性機能の仕様を定める。実装順序は実装計画、進捗はチェックリストに記す。

## 1. 目的と境界

- 人物に任意の型付き属性（生年月日、性別、スキルなど）を登録し、期間付きの履歴として保持する。
- 属性定義ごとに正本を `vault` または `database` とする。Vault 連携人物の Vault 正本属性は、人物ノートの frontmatter を正本として、手動の人物同期で DB へ投影する。
- DB 専用属性は Vault 連携の有無を問わず DB だけで管理し、同期で変更しない。
- 名前・既存の `person_aliases` は人物同定のための別名であり、属性名/選択肢値の alias と混同しない。既存の同定規則を変更しない。
- 人物間リレーションは引き続き DB 専用であり、本機能の同期対象ではない。
- v1 は属性定義管理、人物属性の閲覧、DB 専用値の編集、Vault 正本値の同期・読取専用表示を対象とする。属性検索、AI 公開、Vault への書き戻しは対象外とする。

## 2. 用語と属性定義

- **属性定義**: 値の意味・型・保存元を定める台帳。利用者指定の不変 `key`、表示名、属性名 alias、型、単複、正本種別を持つ。
- **属性値**: 特定の人物・属性定義に対する、型付きの値と任意の有効期間。
- **Vault 正本**: Vault の人物ノートにある値を正とし、同期で DB 投影を置換する属性定義。
- **DB 専用**: Web API/UI からのみ編集する属性定義。

属性定義の `key` は一意かつ作成後不変とする。通常更新で変更できるのは表示名、属性名 alias、選択肢の表示名/alias のみとする。型、単数/複数、正本種別は通常変更不可とするが、将来、値変換・競合検査・プレビューを伴う専用移行で変更できる余地を残す。

### 型と選択肢

- 型は `text`、`date`、`number`、`boolean`、`select` とする。
- `select` の選択肢は不変キー、表示名、値 alias を持つ。値 alias は Vault 入力値を正規の選択肢へ解決するために使う。
- `cardinality` は `single` または `multiple`。単数は異なる値の有効期間が重複してはならず、複数は併存できる。
- 使用中の選択肢は削除できない。選択肢キーも不変とする。

## 3. 値・期間・DB表現

- 値は JSON blob ではなく、人物・属性定義・期間を持つ専用テーブルに型別列で保存する。
- 型別列は `value_text`、`value_date`、`value_number`、`value_boolean`、`option_id` とし、各レコードで定義の型に対応する値列だけを使用する。
- `date` は `YYYY-MM-DD` の文字列、`number` は数値列、`boolean` は SQLite の `0/1`、`select` は選択肢 ID で保存する。API は日付を文字列、真偽を boolean、選択肢を正規キー/表示情報として返す。Vault入力では `YYYY/MM/DD`（月日の1桁表記可）も受け付け、`YYYY-MM-DD` に自動変換して保存する。
- `valid_from` と `valid_until` は任意の `YYYY-MM-DD`。両端を期間に含み、開始日が終了日より後なら拒否する。Vault入力では値と同様に `YYYY/MM/DD`（月日の1桁表記可）も受け付け、`YYYY-MM-DD` に自動変換する。
- 単数属性は、異なる値同士の閉区間/開放区間を含む期間重複を拒否する。完全に同一の値と期間は重複保存しない。
- 将来の検索に備え、属性定義・型別値・期間を対象にしたインデックスを作る。v1 はこれらを検索 API/UI に公開しない。

## 4. Vault frontmatter と同期

Vault 正本属性だけを、人物ノートのトップレベル frontmatter から読む。予約キーは `id`、`name`、`aliases` とする。属性定義キーまたはその alias に一致するキーのみを取り込み、未知キーおよび DB 専用属性に対応するキーは無視する。

期間なしの単一値はスカラーで書ける。複数値、または期間を持つ値は配列とし、配列中ではスカラーと `value` レコードを混在できる。

```yaml
---
id: person_001
name: Example Person
birth_date: "1990-01-01"
skills:
  - php
  - python
  - value: rust
    valid_from: "2026-01-01"
---
```

- スカラーは期間なしの値として扱う。
- 値レコードは `value` 必須、`valid_from` / `valid_until` 任意とする。
- 単数属性には単一スカラーまたは単一値レコードを使う。配列形式でも、単数制約を満たす場合に限り受理する。
- 選択肢は選択肢キー、表示名、値 alias のいずれでも記述でき、DB では正規の選択肢 ID に変換する。
- 同じ属性定義に解決されるキーと alias が同一ノートで併記された場合は不正とする。

同期で正常に読めた人物・属性は、その属性の既存 Vault 投影を全置換する。Vault 正本属性のキーがノートに無い場合は削除として既存投影を削除する。型不一致、未知の選択肢、日付・期間不正、単数制約違反、キー競合があれば、その人物・属性だけ投影を保留して既存値を残し、Vault 入力レポートへ詳細を追加する。他の属性と人物同定同期は継続する。

## 5. 整合性・削除・統合

- DB 専用値は API で作成・更新・削除できる。Vault 正本値の API 書込みは拒否し、Vault 編集と同期を案内する。
- 属性定義の削除は定義、選択肢、全人物の値を物理削除する。Vault ノートは書き換えないため、残った frontmatter キーは以後無視される。UI は影響する属性値件数を表示して確認を求める。
- 人物削除では属性値を外部キー連鎖で削除し、削除結果に属性値件数を含める。
- 人物統合では属性値を同一トランザクションで移管する。完全一致は一本化し、単数属性の期間競合など矛盾があれば、プレビューに表示して統合を拒否する。
- Vault 同期から発生する自動人物統合にも同じ移管規則を使う。競合時はその統合だけをスキップして同期レポートに載せる。

## 6. API / UI / AI 境界

```text
GET    /api/v1/person-property-definitions
POST   /api/v1/person-property-definitions
PATCH  /api/v1/person-property-definitions/{property_definition_id}
DELETE /api/v1/person-property-definitions/{property_definition_id}

GET    /api/v1/people/{person_id}/properties
POST   /api/v1/people/{person_id}/properties
PATCH  /api/v1/people/{person_id}/properties/{property_value_id}
DELETE /api/v1/people/{person_id}/properties/{property_value_id}
```

- 定義作成/更新 API は型、単複、正本種別、alias、選択肢を受ける。通常更新では不変フィールドを受け付けない。
- 人物属性 API は定義情報、値、期間、正本種別を返す。書込み操作は DB 専用定義だけ許可する。
- 属性は専用 API で扱い、既存 `PersonDetail` と AI 向け `people_get` の出力を変更しない。
- 全 API は既存 Bearer 認証で保護する。
- 人物画面に属性定義管理と人物詳細の属性セクションを追加する。Vault 正本値は読取専用で、同期方法と属性ごとのエラーを表示する。

## 7. v1 対象外

- 属性条件による人物検索・絞り込み。
- AI ツール・`people_get` への属性公開、LLM による属性抽出。
- Vault への属性定義/属性値の書き戻し。
- 型・単複・正本種別を変更する汎用編集。
- 部分日付、概算日、日時精度の有効期間。
- 属性値の変更履歴・監査・復元。
