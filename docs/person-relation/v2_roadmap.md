# 人物間リレーション v2 以降ロードマップ

人物間リレーション v1 で対象外とした機能を、日常的な可視性を最優先に、依存関係とリスクに応じて後続バージョンへ配置する。
本書は実装順序の指針であり、各フェーズの着手時には個別計画と仕様決定を行う。

## 共通方針

- v1 の Relation、Relation Type、Evidence の契約を基盤として維持する。互換性を壊す変更には、移行手順と既存データの扱いを明記する。
- 手入力された関係は原典として扱う。推論・AI・自動導出の結果は、出所と根拠を追跡可能な別レイヤーに保持し、手入力を暗黙に上書きしない。
- Vault への書き戻しや AI による変更提案は、プレビューと明示的なユーザー承認を前提とする。
- 時間表現、履歴保持、汎用グラフ化は後からの変更コストが高い。実装前に選択肢と移行方針を決定記録へ残す。

## 実装済みの基盤

- **部分日の表現（2026-09-13）**: 年月・年のみを、偽の完全日付に変換せず保存・表示・検索できる。正規化 ISO 文字列（`YYYY` / `YYYY-MM` / `YYYY-MM-DD`）と境界カラム（`started_on_min` / `ended_on_max`、migration v43）で表現し、順序検証・ステータス判定は境界で行う。重複判定は正規化後の生文字列の完全一致を維持する。AI 投影（`related_people`）には部分日のまま公開する。
- **AI への直接リレーション公開（v4初期版）**: `people_get` を有効化した全エージェントへ、対象人物に直接接続する全リレーション（`related_people` 配列）を公開する。関係メモ・根拠・各種内部 ID は非公開とし、多段探索は行わない。
- **日次要約からのリレーション変更候補抽出**: 日次要約で解決された確定人物に対し、既存有効 Relation Type のリレーション変更候補（create/update/delete）を抽出し、HITL承認（`daily_person_changes`）を経て個別トランザクションで安全に正本へ反映する。適用時には `summary:{summary_id}` を参照先とする Evidence を自動登録する。

## 実装順

### v2 — 人物間リレーション・エクスプローラー

既存の Relation を、人物詳細を一人ずつ開かなくても把握・発見できるようにする。

- **横断一覧と絞り込み**: 全人物の Relation を横断表示し、人物名、Relation Type、状態、期間で絞り込めるようにする。
- **1 hop グラフ表示 UI**: 対象人物を中心に、直接つながる人物と Relation Type を可視化する。初期版は 1 hop の読み取り専用表示に限定し、既存の人物詳細リストを正しい詳細情報への導線として残す。
- **表示上の上限とフィルター**: 表示対象、件数上限、期間、非アクティブな種別の扱いを明示的なフィルターとして設計する。

この段階では、再帰クエリ、専用インデックス、グラフデータベース、多段探索は導入しない。

### v2.1 — 根拠中心の確認・データ整備導線

既存の関係を、根拠と期間の状態から確認し、見直しが必要なデータを発見できるようにする。

- **Evidence 横断閲覧**: Relation をまたいで Evidence を確認できる一覧を追加する。`summary:{summary_id}` のような既知の参照先は元データへの導線を提供し、自由記述の参照先は表示のみとする。
- **見直しフィルター**: 根拠なし、期間不明、終了済みの Relation を抽出できるようにする。自動修正や関係の妥当性判定は行わない。

### v3 — 出来事と時間軸

関係の継続状態と、単発の出来事を区別したまま時系列で理解できるようにする。

- **Person Event / Action モデル**: 人物に紐づく出来事・行動を Relation とは別のドメインとして追加する。Relation Evidence との責務分担、および人物・相手人物・期間・出典の表現を定義する。
- **人物タイムライン**: Relation、Evidence、Event を時系列に閲覧できる表示を追加する。自動導出の結果はこの段階では表示しない。
- **概算日の表現**: 「90年代頃」等の概算表現を、偽の完全日付に変換せず、元の表現・検索用境界・確度を区別して保存、表示、検索できるようにする。現行の `started_on` / `ended_on` との移行・併存方針を決定してから着手する。

### v3.1 — 変更履歴・削除監査・補償復元

外部書き戻しや AI の入力範囲を広げる前に、正本の変更経緯を追跡可能にする。

- Relation、Evidence、Relation Type、Event の作成・更新・削除を追記専用イベントとして保存し、削除済みデータを含めて閲覧可能にする。
- 復元は履歴の書換えではなく、過去スナップショットを反映する補償イベントとして扱う。保持期間と削除済みデータの可視性を事前に定める。

### v4 — AI による候補抽出の拡張

日次要約で実装済みの HITL 承認パターンを、他のノート由来データへ安全に広げる。

- **ノート由来の候補抽出**: 日次要約以外のノートから Relation / Evidence / Event の候補を抽出し、引用箇所、信頼度、既存データとの差分を提示する。保存はユーザー承認後に行い、自動確定はしない。
- **Relation と Event の候補導出**: Event からの Relation 候補、または Relation からの Event 候補を生成する。候補・根拠・承認状態を保存し、手入力の Relation と区別して表示・検索する。

### v5 — 探索・語彙・AI 公開の高度化

利用実績と計測結果が得られた時点で、多段探索と意味的な制約を段階導入する。

- **複数 hop の探索と最適化**: 再帰クエリ、深さ・件数の上限、必要に応じた専用インデックスを導入する。グラフデータベースへの移行は、SQLite の計測結果では不足する場合にのみ検討する。
- **Relation Type の意味モデル**: 型階層、推移性、相互排他制約、関係推論を追加する。各規則には適用範囲、説明可能な根拠、無効化手段を設ける。
- **AI 公開の限定制御・専用監査**: エージェント、Relation Type、人物ごとの公開制御、返却件数上限、専用アクセス監査を、必要性が明確になった時点で設計・導入する。

### v6 — Vault への承認付き書き戻し

履歴・監査と安全な確認ワークフローを前提に、外部データへの反映を導入する。

- **Vault への書き戻し**: Relation、Evidence、Event の Markdown 反映を、差分プレビューと明示承認付きで提供する。競合、既存記述、失敗時の復旧手順を定義する。

## 将来検討 — 汎用グラフ化

人物以外のエンティティも接続する汎用グラフは、人物間リレーションの利用実績だけでは着手しない。対象ドメイン、ID の安定性、権限・削除伝播、検索要件を定義し、既存 Relation を一般化する価値が明確になった場合に別プロジェクトとして計画する。

## v1 で意図的に対応しなかった事項

v1 仕様で除外し、v2 以降の各フェーズ（上記）で扱う。混入防止のため列挙する。

- グラフ描画（可視化 UI）— v2 の 1 hop 表示まで対象外。
- 多段グラフ探索最適化（再帰クエリ・専用索引・グラフ DB 化）— v5。
- Person Event / Action モデル（単発出来事のテーブル化）— v3。
- relation と event の自動導出（行為→状態、状態→行為の推論）— v4。
- 型階層、推移性、排他制約、関係推論（例: 親の親は祖父母）— v5。
- 部分日付のうち概算日（「頃」等）。年月・年・年月日の部分日は実装済み（migration v43）。
- 完全な変更履歴・削除監査 — v3.1。
- Vault への書き戻し（人物ノートへの関係投影）— v6。
- 人物以外（プロジェクト・トピック等）を含む汎用グラフ — 別プロジェクト。

> 補足: 「AI 公開」は v1 対象外だったが、v4 初期版で `people_get` に直接リレーション
> （`related_people`）を公開した（実装済みの基盤・v4 参照）。

## 着手時の確認事項

- 各フェーズ開始前に、対象範囲、API・DB 契約、既存データの移行、テスト方針を個別計画で確定する。
- データ移行、履歴ポリシー、推論規則、Vault 書き戻し、汎用グラフ化のように変更コストと横断影響が大きい判断は、該当する decision record に理由と代替案を記録する。
- ブラウザ E2E は通常の完了条件にせず、バックエンドは `uv run pytest tests/`、フロントエンドは影響範囲に応じたユニットテストと手動確認で検証する。
