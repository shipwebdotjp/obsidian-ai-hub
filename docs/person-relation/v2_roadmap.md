# 人物間リレーション v2 以降ロードマップ

人物間リレーション v1 で対象外とした機能を、依存関係とリスクに応じて後続バージョンへ配置する。
本書は実装順序の指針であり、各フェーズの着手時には個別計画と仕様決定を行う。

## 共通方針

- v1 の Relation、Relation Type、Evidence の契約を基盤として維持する。互換性を壊す変更には、移行手順と既存データの扱いを明記する。
- 手入力された関係は原典として扱う。推論・AI・自動導出の結果は、出所と根拠を追跡可能な別レイヤーに保持し、手入力を暗黙に上書きしない。
- Vault への書き戻しや AI による変更提案は、プレビューと明示的なユーザー承認を前提とする。
- 時間表現、履歴保持、汎用グラフ化は後からの変更コストが高い。実装前に選択肢と移行方針を決定記録へ残す。

## 実装順

### v2 — 履歴・出来事・時間表現の基盤

利用者が関係の根拠と変遷を理解できる状態を先に整える。

- **完全な変更履歴・削除監査**: Relation、Evidence、Relation Type の作成・更新・削除を追跡できる履歴モデルと閲覧方法を追加する。保持期間、削除済みデータの可視性、復元可否を事前に定める。
- **Person Event / Action モデル**: 人物に紐づく出来事・行動を Relation とは別のドメインとして追加する。Relation Evidence との責務分担、および人物・期間・出典の表現を定義する。
- **部分日・概算日の表現**: 年月のみ、期間、概算などを、偽の完全日付に変換せず保存・表示・検索できるようにする。現行の `started_on` / `ended_on` をどう移行・併存させるかを決定してから着手する。

完了条件は、既存の完全日付データを失わずに移行でき、履歴と時間精度が UI・API で一貫して説明できることとする。

### v2.1 — 人物グラフの閲覧

v1 の人物間 Relation を読み取り専用で俯瞰できるようにする。

- **グラフ表示 UI**: 対象人物を中心に、直接つながる人物と Relation Type を可視化する。表示対象・件数上限・期間・非アクティブな種別の扱いをフィルターとして設計する。
- 初期版は 1 hop の表示に限定し、既存の人物詳細リストを正しい詳細情報への導線として残す。

この段階では、再帰クエリ、専用インデックス、グラフデータベースは導入しない。

### v3 — 探索と関係語彙の高度化

データ量と利用目的が明確になった時点で、多段探索と意味的な制約を追加する。

- **複数 hop の探索と最適化**: 再帰クエリ、深さ・件数の上限、必要に応じた専用インデックスを導入する。グラフデータベースへの移行は、SQLite の計測結果では不足する場合にのみ検討する。
- **Relation Type の意味モデル**: 型階層、推移性、相互排他制約、関係推論を段階的に追加する。各規則には適用範囲、説明可能な根拠、無効化手段を設ける。
- **Relation と Event の自動導出**: v2 の Event モデルを基礎に、出来事からの関係候補または関係からの出来事候補を生成する。自動確定は行わず、候補・根拠・承認状態を保存する。

このフェーズの推論結果は、手入力の Relation と区別して表示・検索できなければならない。

### v4 — 外部書き戻しと AI 支援

人が確認できる安全なワークフローを整えたうえで、外部連携と AI を導入する。

- **Vault への書き戻し**: Relation、Evidence、Event の Markdown 反映を、差分プレビューと承認付きで提供する。競合・既存記述・ロールバックの扱いを定義する。
- **AI への直接リレーション公開 (v4初期版・実装済み)**: `people_get` を有効化した全エージェントへ、対象人物に直接接続する全リレーション（`related_people` 配列）を公開する。件数上限・専用監査・アクセス制御は設けず、関係メモ・根拠・各種内部 ID は非公開とし、多段探索は行わない。
- **将来の限定公開制御・多段探索 (未設計)**: 将来の必要性に応じて、リレーションのアクセス制御・件数上限、専用監査ログ、および複数 hop の多段探索モデルを設計・導入する。
- **LLM による関係抽出**: ノート等から Relation / Evidence / Event の候補を抽出し、根拠箇所と信頼度を提示する。保存はユーザー承認後に行う。
- **日次要約からのリレーション変更候補抽出（実装済み）**: 日次要約で解決された確定人物に対し、既存有効Relation Typeのリレーション変更候補（create/update/delete）を抽出し、HITL承認（`daily_person_changes`）を経て個別トランザクションで安全に正本へ反映する。適用時には `summary:{summary_id}` を参照先とする Evidence を自動登録する。

## 将来検討 — 汎用グラフ化

人物以外のエンティティも接続する汎用グラフは、人物間リレーションの利用実績だけでは着手しない。対象ドメイン、ID の安定性、権限・削除伝播、検索要件を定義し、既存 Relation を一般化する価値が明確になった場合に別プロジェクトとして計画する。

## 着手時の確認事項

- 各フェーズ開始前に、対象範囲、API・DB 契約、既存データの移行、テスト方針を個別計画で確定する。
- データ移行、履歴ポリシー、推論規則、Vault 書き戻し、汎用グラフ化のように変更コストと横断影響が大きい判断は、該当する decision record に理由と代替案を記録する。
- ブラウザ E2E は通常の完了条件にせず、バックエンドは `uv run pytest tests/`、フロントエンドは影響範囲に応じたユニットテストと手動確認で検証する。
