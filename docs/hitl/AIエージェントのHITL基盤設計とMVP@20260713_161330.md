理想は、プロトコルを定義してどのAIエージェントからでもキューに接続できるようにしたい。  
  
ポーリングもしくはWebhookで人間の応答を取得して再開するっていう流れなんだけど、一旦セッションが終了した後でもその応答を元にやるためには、結局AIツール側でどのタスクを実行中で、何を人間に尋ねているのか、その状態を保存しておかないと難しいじゃんね。結局そのね、コンテキストが失われちゃってる状態で応答をもらっても意味をなさないわけだから、その状態保存が結構難しいよね。同じね、プロセス内でね、なんかやるんだったら比較的簡単なんだけど、一旦外部プロセスに、しかもその待ちがいつ応答が来るかわからないし、自分自身のプロセスもそのうち終了させられる可能性すらある。そういう状況だと、どういうデータ構造、仕組みが必要になるかな。

## 7. Human-in-the-Loop質問キューの設計  
  
### 7.1 人間に聞くべき条件  
  
AIがすべてを自動判断すると危険である一方、細かい事項を毎回尋ねると使いにくくなる。したがって、判断を求める条件を明示する。  
  
人間に確認すべき代表的条件は次のとおりである。  
  
- 永続記憶を追加、変更、削除するとき  
- 宗教、健康、心理、人間関係の記憶を扱うとき  
- 二つの記録が矛盾するとき  
- メール送信、投稿、削除など外部へ影響する操作  
- 金銭や契約に関する操作  
- 相手の意図や感情について確信が低いとき  
- 回答候補が複数あり、価値判断が必要なとき  
- 指定期限までに回答がなければ処理方針が変わるとき  
  
### 7.2 キューのデータ構造  
  
現時点で、あらゆる個人AIやエージェントが共通して利用する、単一のHITL質問プロトコルが確立しているとは言い難い。そのため、特定フレームワークに依存しない永続キューを中心に置くのがよい。

エージェント側は、質問を送信したらタスク状態を永続化して停止する。回答はWebhook、ポーリング、メッセージキューのいずれかで受け取り、同じタスクIDから再開する。  
  
### 7.3 通知チャネルと回答画面を分離する  
  
通知先は、デスクトップ、Web、メール、LINEなど複数あってよい。ただし、質問そのものと通知チャネルを密結合させない方がよい。  
  
```text

   ↓  
HITL API / Queue  
   ├─ Desktop notification  
   ├─ Web dashboard  
   ├─ Email  
   └─ Messaging adapter  
```  
  
センシティブな内容については、通知本文に詳細を書かず、「確認が必要な項目があります」とだけ表示し、認証された画面で内容を確認する。  
```
[Timestamp: 2026/07/13 16:13:30]

**ai**: おっしゃる通りで、これは単なる「質問キュー」ではなく、**長時間・中断耐性を持つワークフロー／継続（continuation）基盤**として設計する必要があります。

人間の応答だけを保存しても不十分で、少なくとも次を永続化しなければ再開できません。

1. **何のタスクだったか**
2. **どの実行地点で停止したか**
3. **その時点での入力・中間状態・外部操作の実行済み状況**
4. **何を質問し、どの回答を待っているか**
5. **回答後にどのエージェント／コード／環境で再開するか**

つまり、AIプロセスを生かしたまま待つのではなく、AIを「いつでも死ねるワーカー」とみなし、状態を外部に退避する設計が必要です。

# 全体像

推奨する責務分離はこのような形です。

```text
┌──────────────────┐
│ AI Agent / Tool   │
│  - タスクを実行    │
│  - 質問を作る      │
│  - checkpoint保存 │
└────────┬─────────┘
         │ Protocol API
         ▼
┌──────────────────────────────────┐
│ HITL Workflow Service             │
│                                  │
│ - Task / Run 状態管理             │
│ - Question Queue                  │
│ - 回答管理                        │
│ - タイムアウト・デフォルト処理     │
│ - イベントログ／Outbox             │
│ - Webhook / Polling / Event配信   │
└───────┬──────────────┬───────────┘
        │              │
        ▼              ▼
  Human UI / API    Notification adapters
  Web / Slack etc.  Email / Push / LINE etc.

        │ 人間が回答
        ▼
┌──────────────────────────────────┐
│ Resume Dispatcher / Worker        │
│ - 回答イベントを受信              │
│ - 対象Runをキューへ投入           │
│ - 任意のワーカーが再開            │
└──────────────────────────────────┘
```

重要なのは、**Human UI は「回答を書き込むだけ」**、**Resume Dispatcher は「再開ジョブを起動するだけ」**にすることです。

UIやWebhook受信元が、特定エージェントのプロセスへ直接コールバックする構造は避けた方がよいです。そのプロセスは既に終了しているかもしれないからです。

# 基本原則：エージェントは停止可能・再実行可能にする

各エージェントは次のような実装モデルになります。

```python
def run(task_context):
    state = load_checkpoint(task_context.run_id)

    # 途中までの結果を基に処理を続ける
    result = do_step_1(state)

    if requires_human_approval(result):
        checkpoint = {
            "step": "awaiting_approval",
            "draft": result,
            "external_effects": state["external_effects"],
        }

        save_checkpoint(run_id, checkpoint)

        question = create_question(...)
        create_question_and_suspend_run(run_id, question)

        return Suspend()  # プロセス終了してよい

    return do_next_step(result)
```

回答後は別プロセス・別マシン・別バージョンのワーカーでも、原則として以下のように再開できます。

```python
def resume(run_id, question_id):
    run = load_run(run_id)
    question = load_question(question_id)
    checkpoint = load_checkpoint(run_id)

    assert question.status == "answered"
    assert checkpoint["step"] == "awaiting_approval"

    return continue_from_approval(
        checkpoint=checkpoint,
        human_answer=question.answer,
    )
```

ここで必要なのは「元のLLM会話をそのまま復元すること」ではなく、**再開に必要な最小の決定可能状態を保存すること**です。

# 保存すべきデータ構造

質問単体ではなく、少なくとも次の4種類を分けると扱いやすいです。

- `Task`: 論理的な仕事単位。例: 「週次レビュー」
- `Run`: Taskの1回の実行単位。リトライや再実行を区別する
- `Checkpoint`: 再開のためのアプリケーション状態
- `Question`: 人間への確認・入力要求
- `Event`: 状態変更の監査ログ、外部連携の起点

---

## 1. Task

長期的な仕事の識別子です。

```json
{
  "task_id": "task_01JXYZ...",
  "tenant_id": "org_acme",
  "agent_id": "weekly-review-agent",
  "agent_version": "2026.07.12",
  "workflow_name": "weekly_review",
  "idempotency_key": "weekly-review:2026-W28",
  "status": "active",
  "created_at": "2026-07-12T10:00:00Z",
  "updated_at": "2026-07-12T10:03:00Z"
}
```

`agent_version` は重要です。数週間後に回答が来た時、同じロジックで再開するのか、最新版でマイグレーションするのかを決める必要があります。

---

## 2. Run

タスクの一回の実行状態です。

```json
{
  "run_id": "run_01JXYZ...",
  "task_id": "task_01JXYZ...",
  "attempt": 1,
  "status": "waiting_for_human",
  "current_step": "approve_memory_candidate",
  "input_ref": {
    "uri": "s3://hitl-data/runs/run_01JXYZ/input.json",
    "sha256": "..."
  },
  "checkpoint_ref": {
    "uri": "s3://hitl-data/runs/run_01JXYZ/checkpoint-v3.json",
    "sha256": "..."
  },
  "waiting_question_id": "q_01JXYZ...",
  "resume_token_version": 3,
  "lease": null,
  "created_at": "2026-07-12T10:00:00Z",
  "updated_at": "2026-07-12T10:02:00Z"
}
```

状態の例です。

```text
created
→ queued
→ running
→ waiting_for_human
→ queued_for_resume
→ running
→ completed

例外:
→ failed
→ cancelled
→ expired
→ needs_migration
```

質問の状態とRunの状態は関連しますが、同一視しない方がよいです。

- Question: 人間の意思決定の状態
- Run: エージェント実行の状態

です。

---

## 3. Checkpoint / Continuation

最も重要な部分です。

再開に必要な状態をJSON等の安全にシリアライズできる形式で保存します。

```json
{
  "schema_version": 3,
  "workflow": "weekly_review",
  "step": "approve_memory_candidate",

  "input": {
    "week": "2026-W28",
    "user_id": "user_123"
  },

  "derived_state": {
    "candidate_memory": {
      "text": "期限付き準備より開発作業を優先しやすい傾向がある",
      "confidence": 0.72,
      "evidence_ids": ["note_17", "calendar_42"]
    }
  },

  "pending_action": {
    "type": "write_long_term_memory",
    "idempotency_key": "memory:user_123:candidate_8d9f"
  },

  "resume": {
    "handler": "weekly_review.resume_after_memory_approval",
    "expected_question_id": "q_01JXYZ...",
    "expected_answer_schema_version": 1
  },

  "completed_steps": [
    {
      "step": "collect_notes",
      "completed_at": "2026-07-12T10:00:04Z",
      "output_ref": "s3://hitl-data/..."
    }
  ],

  "external_effects": [
    {
      "effect_id": "effect_01...",
      "type": "calendar_read",
      "idempotency_key": "calendar-read:...",
      "status": "completed"
    }
  ]
}
```

### 保存するべきもの

- ワークフロー名、現在のステップ
- 初期入力
- 中間生成物
- 根拠データの参照
- 後続操作の予定
- 実行済み外部操作の記録
- 再開ハンドラ名
- 期待する回答スキーマのバージョン
- LLMに再投入する必要がある要約・メッセージ履歴・ツール結果

### 保存すべきでないもの

- Python/Nodeのスタックフレーム
- メモリアドレス
- 開いたソケット
- インメモリDB接続
- 「現在動いているモデルの内部状態」そのもの

これらを永続化して任意時点に復元するのは一般に脆いです。代わりに、**業務ワークフローとして再実行可能な明示的状態機械**に落とします。

# LLMのコンテキストをどう保存するか

ここは二段階に分けるとよいです。

## A. 業務上の正規状態

これは構造化して保存します。

```json
{
  "selected_customer_id": "cus_123",
  "invoice_draft_id": "inv_draft_456",
  "approval_required": true,
  "approval_reason": "金額が10万円を超えるため"
}
```

これは再開の正とします。

## B. LLM用の再構成コンテキスト

会話履歴全部を無制限に持つのではなく、以下を保存します。

- システムプロンプト／エージェント定義のバージョン
- 元のユーザー要求
- 重要なツール呼び出しと結果
- 決定事項
- 中間成果物
- 会話要約
- 保留質問と回答
- 根拠資料の参照

再開時に、この情報からコンテキストを組み立て直します。

```text
[タスク目的]
請求書案を作成し、送信前に承認を得る。

[既に完了した操作]
- 顧客情報を取得済み
- 請求書ドラフト inv_draft_456 を作成済み
- メールは未送信

[保留していた判断]
- 120,000円の請求書を送信してよいか人間の承認待ち

[人間の回答]
- approve

[次に行うこと]
- 承認済みドラフトを送信する
- 送信操作は idempotency_key=send:inv_draft_456 を使う
```

LLMの全文履歴は監査・デバッグ用に保存してもよいですが、**再開の唯一の根拠にしない**方が安全です。要約だけに依存するのも危険なので、重要な事実は構造化状態に置きます。

# 汎用プロトコルとして定義するなら

特定のAIフレームワークに依存しないよう、HTTP + JSONを基本にするのが現実的です。エージェント接続方式としてはMCPサーバーを提供してもよいですが、MCPだけに依存せず、まずは通常のAPIを正とするのがよいです。

最低限、以下の操作が必要です。

```text

POST   /v1/runs/{run_id}/checkpoint
POST   /v1/questions
GET    /v1/questions/{question_id}
POST   /v1/questions/{question_id}/answers
POST   /v1/runs/{run_id}/claim
POST   /v1/runs/{run_id}/complete
POST   /v1/runs/{run_id}/fail
GET    /v1/events?cursor=...
```

## 質問作成API

質問作成とRunの停止状態への遷移は、**DBトランザクションで同時に確定**させるべきです。

```http
POST /v1/questions
Idempotency-Key: ask:run_01JXYZ:approve_memory_candidate:v1
```

```json
{
  "run_id": "run_01JXYZ...",
  "question_key": "approve_memory_candidate",
  "type": "approval",
  "title": "この傾向を長期記憶として保存しますか？",
  "body": {
    "summary": "期限付き準備より開発作業を優先しやすい傾向が検出されました。",
    "evidence_refs": ["note_17", "calendar_42"]
  },
  "answer_schema": {
    "type": "object",
    "required": ["decision"],
    "properties": {
      "decision": {
        "type": "string",
        "enum": ["approve", "episode_only", "reject"]
      },
      "comment": {
        "type": "string",
        "maxLength": 2000
      }
    }
  },
  "default_resolution": {
    "on_expiry": {
      "decision": "episode_only"
    }
  },
  "risk_level": "medium",
  "expires_at": "2026-07-19T14:59:59Z",
  "resume_policy": {
    "mode": "enqueue_run",
    "dedupe_key": "resume:run_01JXYZ:question_approve_memory_candidate"
  }
}
```

サーバー側では概念的に以下を一つのトランザクションで行います。

```text
1. checkpoint を保存
2. question を created / waiting_for_human で作成
3. run.status を waiting_for_human に変更
4. QuestionCreated イベントを outbox に追加
5. commit
```

その後、Outbox Relayがイベントを通知サービス、Webhook、メッセージブローカーなどへ配信します。

この **Transactional Outbox パターン** を使うと、

- DBには質問があるが通知されなかった
- 通知されたがDBには質問がない
- 回答があるのに再開イベントが消えた

といった不整合をかなり防げます。

# 回答から再開まで

人間がUI、Slack、メールリンク、外部APIなどで回答します。

```http
POST /v1/questions/q_01JXYZ/answers
Idempotency-Key: answer:q_01JXYZ:user_123:request_abc
```

```json
{
  "answer": {
    "decision": "approve",
    "comment": "この内容で保存してよいです"
  },
  "actor": {
    "type": "human",
    "id": "user_123"
  },
  "expected_question_version": 4
}
```

サーバー側では以下を実施します。

```text
1. 回答者が権限を持つか検証
2. question が waiting_for_human か確認
3. 回答を answer immutable record として保存
4. question.status = answered
5. run.status = queued_for_resume
6. HumanAnswerReceived / RunResumeRequested イベントをOutboxに記録
7. commit
```

Resume Dispatcherがイベントを消費してジョブキューに入れます。

```json
{
  "event_type": "run.resume_requested",
  "run_id": "run_01JXYZ...",
  "question_id": "q_01JXYZ...",
  "answer_id": "ans_01JXYZ..."
}
```

任意のRunnerがRunをclaimし、checkpointと回答をロードして再開します。

# ポーリング・Webhook・メッセージキューの使い分け

これらは本質的には「回答イベントをどう配送するか」の違いです。

## ポーリング

エージェント側が以下のように確認します。

```http
GET /v1/runs/{run_id}
GET /v1/questions/{question_id}
```

利点:

- 最初に実装しやすい
- 外部から到達できないローカル環境でも使える
- Webhook受信サーバーが不要

欠点:

- 長期間ポーリングするプロセス自体を維持する必要がある
- 待機コストと遅延がある

そのため、エージェントプロセスが終了する前提なら、「エージェントがずっとポーリングする」のはあまり理想的ではありません。中央のDispatcherがポーリングやイベント受信を担当し、ワーカーを起動する方がよいです。

## Webhook

Webhookは外部のエージェント実行基盤に「再開要求」を渡すために有効です。

ただしペイロードに回答本文や機密情報を直接入れるより、次の程度に留める方がよいです。

```json
{
  "event_id": "evt_01...",
  "event_type": "run.resume_requested",
  "run_id": "run_01JXYZ",
  "question_id": "q_01JXYZ",
  "occurred_at": "2026-07-12T10:12:00Z"
}
```

受信側はAPIから認可付きで詳細を取得します。

Webhookには必ず以下が必要です。

- HMAC署名
- タイムスタンプとリプレイ防止
- リトライ
- 指数バックオフ
- at-least-once配送前提の重複排除
- 配信失敗のDLQ（dead-letter queue）

## メッセージキュー

大量のタスクや信頼性が必要なら、内部ではこれが最も扱いやすいです。

```text
question.answered
  → workflow.resume.requested
  → agent.run.queue
  → worker claims run
```

SQS、RabbitMQ、Kafka、Redis Streams、Cloud Tasksなどは選択肢です。ただし、キューは状態の正本ではありません。**正本はDB上のTask / Run / Question / Checkpoint**です。

メッセージは消えてもDBをスキャンして復旧できる設計にします。

---

# 冪等性は必須

AIワークフローでは、再試行や二重配送が必ず起きます。

例えば「メール送信」の直後にワーカーが落ちた場合、

```text
メール送信成功
→ DBへの完了記録前にプロセス死亡
→ Run再実行
→ 同じメールをもう一度送ってしまう
```

という事故が起こります。

したがって外部副作用には必ず `idempotency_key` を付けます。

```json
{
  "operation": "send_email",
  "idempotency_key": "send-email:run_01JXYZ:step_send_invoice:v1"
}
```

外部APIが冪等キーをサポートしない場合も、こちら側で `effects` テーブルを持ちます。

```json
{
  "effect_id": "eff_01...",
  "run_id": "run_01JXYZ",
  "step": "send_invoice",
  "idempotency_key": "send-email:run_01JXYZ:step_send_invoice:v1",
  "status": "started",
  "request_ref": "s3://...",
  "response_ref": null
}
```

原則は次です。

- 外部操作の前に「開始予定」を記録
- 冪等キーを使って外部操作
- 結果を記録
- 再実行時は既存effectを確認
- 不明状態なら「再送」ではなく照会・補償フローへ進む

---

# 状態遷移の設計

提示された状態遷移はよい出発点です。ただし本番では「質問」と「実行」を分けて管理するのがおすすめです。

## Question

```text
draft
→ open
→ answered
→ consumed
→ closed

例外:
→ expired
→ cancelled
→ superseded
```

- `open`: 回答可能
- `answered`: 回答は記録されたが、エージェントが未処理
- `consumed`: 再開処理が回答を取り込んだ
- `closed`: ワークフロー全体として確定

## Run

```text
created
→ queued
→ running
→ waiting_for_human
→ queued_for_resume
→ running
→ completed

例外:
→ failed
→ cancelled
→ timed_out
→ needs_manual_recovery
```

「Questionがansweredになった」ことと「Runが正常再開・完了した」ことは別です。再開したエージェントが失敗することもあるためです。

---

# タイムアウトとデフォルト処理

質問の期限切れも、人間回答と同じくイベント化します。

```text
QuestionExpired
→ デフォルト回答を確定する
→ RunResumeRequested
→ 再開する
```

ただし、リスクごとに挙動を変えるべきです。

| リスク | 期限切れ時の推奨 |
|---|---|
| 低 | 明示したデフォルトで継続 |
| 中 | 安全側のデフォルトで継続、後で通知 |
| 高 | 自動実行せず `expired` / `needs_manual_review` |
| 不可逆・金銭・契約 | 原則キャンセルまたは明示承認待ちを維持 |

たとえば「長期記憶への保存」は未回答なら保存しない、「メール送信」は未回答なら送信しない、が安全側です。

# 質問は“UI文言”ではなく“意思決定契約”として持つ

エージェント間共通化を目指すなら、質問を単なるテキストではなく、型・回答スキーマ・副作用情報を持つ契約にします。

代表的な `question_type` は例えば以下です。

```text
approval          : 実行可否
selection         : 選択肢から選ぶ
free_text         : 追加入力を得る
clarification     : 曖昧な要求を解消する
credential_request: 認証・秘密情報の提供を求める
conflict_resolution: 矛盾を人間に解消してもらう
review            : 成果物をレビューしてもらう
```

さらに、UIが共通レンダリングできるようJSON Schemaで回答を定義します。

```json
{
  "type": "object",
  "required": ["approved"],
  "properties": {
    "approved": {
      "type": "boolean"
    },
    "reason": {
      "type": "string",
      "maxLength": 1000
    }
  }
}
```

これにより、エージェント固有のフロントエンドを作らなくても、共通のWebダッシュボード、Slackフォーム、CLIなどが質問を表示・回答できるようになります。

# セキュリティと監査

この仕組みは「人間の承認によりAIが外部操作を実行する」ため、セキュリティ上かなり重要です。

最低限必要なものは以下です。

- tenant / organization / user の厳密な分離
- 回答者の認可  
  - 誰でも答えられるのか
  - 所有者のみか
  - 複数人承認が必要か
- 質問内容・根拠資料へのアクセス制御
- 監査ログ  
  - 誰が、いつ、何を見て、どの回答をしたか
- 回答の追記・訂正ではなく、原則immutableな履歴
- Webhook署名検証
- 機密情報を通知本文に出さない
- 監査・デバッグ用のLLMプロンプトログを暗号化・保持期限管理する
- プロンプトインジェクション由来の「偽の承認要求」対策  
  - 質問の起票元、対象操作、根拠、ポリシー判定を記録する

特に高リスク操作では、回答時に質問内容のハッシュや対象リソースのバージョンを結びつけるとよいです。

```json
{
  "question_snapshot_hash": "sha256:...",
  "target_resource_version": "invoice_draft_456:v7",
  "answer": {
    "decision": "approve"
  }
}
```

これにより、承認後に対象の請求書内容が差し替わる、といった事故を防ぎやすくなります。

# 重要な設計判断

## 「元エージェントにWebhookする」より「中央基盤が再実行をスケジュールする」

避けたい形です。

```text
Human response
→ callback URL
→ 以前のAIプロセスに直接送る
```

推奨形です。

```text
Human response
→ HITL基盤に永続化
→ ResumeRequested event
→ Runをジョブキューに投入
→ 利用可能なワーカーがcheckpointから再開
```

これなら元プロセス、元コンテナ、元マシンが消えていても問題ありません。

## 「LLM会話履歴」より「明示的な業務状態」を正とする

会話履歴だけで復元すると、モデル変更・要約欠落・コンテキスト長制限・プロンプト注入などに弱いです。

```text
構造化されたCheckpoint = 正本
会話履歴・要約 = LLMが判断するための補助情報
```

という位置付けが堅牢です。

## 「Exactly once」は狙わず、「At least once + 冪等性」にする

分散システムで完全な一回だけ実行は高コストです。現実的には、

- イベントは重複して届く前提
- 再開要求は複数回起きうる前提
- ワーカーは途中で死ぬ前提
- 外部副作用は冪等キーで守る

という設計にします。

# まとめ

必要なのは、人間回答を待つAIのための単なるキューではなく、以下を備えた**耐障害性ワークフロー基盤**です。

- `Task / Run / Checkpoint / Question / Answer / Event / Effect` を分離して永続化する
- 質問作成とRun停止を原子的に処理する
- 回答と再開要求をイベントとして扱う
- 回答後は元プロセスへの復帰ではなく、任意ワーカーがCheckpointから再開する
- LLM履歴ではなく構造化状態を正本とする
- 外部操作には冪等キーと副作用ログを持たせる
- 期限切れ・取消・再試行・重複イベントを状態遷移として扱う
- HTTP/JSONをコアプロトコルにし、MCP・Webhook・ポーリング・メッセージキューをアダプタとして提供する

一言で表すなら、設計対象は **“human-in-the-loop queue” ではなく “durable agent continuation protocol”** です。

## MVPで残すべき最小要件

プロセスが死んでも再開できるために、削れないのは実質この4つだけです。

1. **Run ID**
   - どの実行を再開するか識別するID

2. **Checkpoint**
   - 停止した地点と、再開に必要な状態
   - JSONで保存すればよい

3. **Question**
   - 人間に何を聞いているか
   - 選択肢、回答、期限、状態

4. **再開トリガー**
   - 回答済みのRunを次回ワーカーが見つけて再開する仕組み

つまり、最小の概念モデルはこれだけです。

```text
Run
 ├─ checkpoint_json
 ├─ status
 └─ Question（必要な場合のみ）
```

`Task` と `Run` を分離する必要すら、最初はありません。

# 削れるもの

## 1. Webhookは不要

ローカル用途であれば、最初はWebhookを実装しなくてよいです。

代わりに、エージェントランナーが起動時・定期実行時に回答済みRunを探します。

```text
cron / launchd / systemd timer
    ↓
runner
    ↓
SQLiteで status = 'ready' のRunを取得
    ↓
checkpointを読んで再開
```

あるいはCLIで明示的に実行してもよいです。

```bash
hitl list
hitl answer q_123 approve
hitl resume
```

人間が回答した瞬間に再開する必要がなければ、ポーリングすら不要です。

---

## 2. メッセージキューは不要

SQS、Redis、RabbitMQ、Kafkaなどは不要です。

SQLiteのテーブルをそのままキューとして使えます。

```sql
SELECT *
FROM runs
WHERE status = 'ready_to_resume'
ORDER BY updated_at
LIMIT 1;
```

1台のローカルマシン、通常は1ワーカーならこれで十分です。

---

## 3. Task / Run の分離は不要

本格版では、論理タスクと実行試行を分離しますが、MVPでは一つにまとめられます。

```json
{
  "run_id": "run_01",
  "agent": "weekly-review",
  "status": "waiting",
  "step": "approve_memory",
  "checkpoint": {},
  "created_at": "2026-07-12T10:00:00Z"
}
```

失敗時のリトライ履歴、実行試行番号、親子タスクなどが必要になってから分離すればよいです。

---

## 4. 多様な質問タイプは不要

最初は質問を2種類程度に限定できます。

```text
choice   : 選択肢から一つ選ぶ
text     : 自由入力
```

あるいは、さらに単純に全質問を次の形式に統一できます。

```json
{
  "prompt": "メールを送信しますか？",
  "options": [
    { "id": "yes", "label": "送信する" },
    { "id": "no", "label": "送信しない" }
  ],
  "answer": null
}
```

JSON Schema、動的フォーム、複数回答者、承認フローは後回しで構いません。

---

## 5. 通知連携は不要

最初は専用のWeb UIすら不要です。

例えば以下のいずれか一つで十分です。

- CLI
- ローカルWeb画面
- macOS通知 + ローカルWeb画面へのリンク
- SlackやLINEではなく、ターミナルで一覧表示

CLIだけの例です。

```bash
$ hitl pending

q_01  [weekly-review]
長期記憶として保存しますか？
1. 保存する
2. 今回だけ記録する
3. 保存しない

$ hitl answer q_01 2
回答を保存しました。

$ hitl resume
weekly-review を再開しました。
```

通知が欲しくなった段階で、OS通知を一つだけ足せばよいです。

---

## 6. 認証・RBAC・マルチテナントは不要

個人ローカル用なら削れます。

不要なもの:

- organization / tenant
- ユーザー管理
- OAuth
- 回答権限
- 複数段階承認
- 監査用の複雑なアクセス制御

ただし、将来クラウドに出す可能性があるなら、テーブルに `owner_id` を置いておく程度は悪くありません。現時点では固定値 `"local"` でよいです。

---

## 7. Outbox、イベントソーシングは不要

SQLiteでローカル運用するなら、最初はイベント配信基盤を作らなくてもよいです。

以下のように、回答登録時にRunの状態も同一トランザクションで変えれば足ります。

```sql
BEGIN;

UPDATE questions
SET status = 'answered',
    answer_json = :answer,
    answered_at = CURRENT_TIMESTAMP
WHERE question_id = :question_id
  AND status = 'waiting';

UPDATE runs
SET status = 'ready_to_resume',
    updated_at = CURRENT_TIMESTAMP
WHERE waiting_question_id = :question_id;

COMMIT;
```

通知失敗、Webhook再試行、イベントの配送保証などが必要になった時点でOutboxを導入すればよいです。

# 最小データベース設計

SQLiteの2テーブルで開始できます。

```sql
CREATE TABLE runs (
  run_id TEXT PRIMARY KEY,
  agent_name TEXT NOT NULL,
  status TEXT NOT NULL,
  step TEXT NOT NULL,

  checkpoint_json TEXT NOT NULL,

  waiting_question_id TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,

  error_message TEXT
);

CREATE TABLE questions (
  question_id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL,

  prompt TEXT NOT NULL,
  context TEXT,
  options_json TEXT,
  answer_json TEXT,

  status TEXT NOT NULL,
  created_at TEXT NOT NULL,
  answered_at TEXT,

  FOREIGN KEY (run_id) REFERENCES runs(run_id)
);
```

`checkpoint_json` の例です。

```json
{
  "version": 1,
  "step": "approve_memory",
  "resume_handler": "weekly_review.after_memory_approval",

  "input": {
    "week": "2026-W28"
  },

  "state": {
    "memory_candidate": {
      "text": "期限付き準備より開発作業を優先しやすい傾向がある",
      "confidence": 0.72
    }
  }
}
```

質問はこうです。

```json
{
  "question_id": "q_01",
  "run_id": "run_01",
  "prompt": "この傾向を長期記憶として保存しますか？",
  "context": "7月10日の記録から検出されました。",
  "options_json": [
    { "id": "approve", "label": "保存する" },
    { "id": "episode_only", "label": "今回だけ記録する" },
    { "id": "reject", "label": "保存しない" }
  ],
  "status": "waiting"
}
```

# エージェント向けの最小API

最初はライブラリとして提供する方が、HTTP APIより簡単です。

Pythonなら概念的には次の程度です。

```python
from hitl import wait_for_human

answer = wait_for_human(
    run_id=run_id,
    step="approve_memory",
    checkpoint={
        "memory_candidate": candidate,
        "resume_handler": "weekly_review.after_memory_approval"
    },
    prompt="この傾向を長期記憶として保存しますか？",
    options=[
        {"id": "approve", "label": "保存する"},
        {"id": "episode_only", "label": "今回だけ記録する"},
        {"id": "reject", "label": "保存しない"}
    ]
)
```

ただし、この関数は本当に待機しません。

内部では以下を行い、専用例外を投げてプロセスを終了させます。

```python
save_checkpoint(...)
create_question(...)
mark_run_waiting(...)
raise SuspendRun()
```

再開側は、回答済みRunを拾って実行します。

```python
def resume(run):
    checkpoint = json.loads(run.checkpoint_json)
    question = load_question(run.waiting_question_id)
    answer = json.loads(question.answer_json)

    handler = resolve(checkpoint["resume_handler"])
    handler(checkpoint, answer)
```
